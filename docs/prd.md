# 교회 찬양 슬라이드 제작 서비스 PRD

## 1. 개요

교회 찬양팀·미디어 담당자가 찬양 가사와 움직이는 배경을 조합해, 가독성 높은 예배용 슬라이드쇼를 웹에서 빠르게 만들고 바로 송출하는 경량 제작 도구다.

미리캔버스·캔바 같은 범용 디자인 툴의 '교회 찬양 특화 경량판'으로 포지셔닝한다. 자유 배치형 디자인 에디터가 아니라, 가사를 슬라이드로 바꾸고 곡 단위로 배경을 입히는 구조화된 편집기에 집중한다.

핵심 차별점은 움직이는 배경(모션 배경)이다. 곡마다 영상·애니메이션 배경을 지정하고, 그 위에 오버레이와 텍스트 가독성 설정을 얹어 곧바로 예배 화면으로 쓴다.

핵심 기능:

- 찬양 가사 입력 및 슬라이드 분할
- 곡 단위 배경 지정 (움직이는 배경 중심)
- 배경 위 검정 오버레이 + 불투명도 조절
- 웹폰트 기반 폰트 선택, 글자 크기, 그림자 등 가독성 설정
- 사용자가 만든 찬양 슬라이드를 공개·공유하고 검색해 바로 가져다 쓰는 공유 라이브러리 (같은 곡도 여러 버전이 공존하는 게시판, 가져간 횟수순)
- 만든 슬라이드와 배경을 한곳에서 보는 곡 라이브러리·배경 갤러리 화면
- 관리자가 앱에서 올리는 기본 제공 배경(영상·이미지). 사용자 업로드는 없다 (2026-09-24)

**문제 정의:** 중소형 교회 대부분은 PowerPoint·Keynote로 가사 슬라이드를 만든다.

- 매주 가사를 찾아 붙여넣고, 슬라이드마다 서식을 다시 맞추는 반복 작업이 크다
- 움직이는 배경을 쓰려면 영상을 구해 슬라이드마다 넣어야 하고, 슬라이드가 바뀔 때 배경 영상이 자연스럽게 이어지지 않는다
- ProPresenter·EasyWorship 같은 전문 송출 프로그램은 유료 라이선스와 설치형 PC가 필요해 봉사자 중심 교회에 부담이다

이 서비스는 설치 없는 무료 웹 도구로, 가사 입력부터 모션 배경 송출까지를 한 흐름으로 묶는다.

## 2. 목표와 비목표

이 서비스는 사역용 무료 공개 서비스다. 목표는 수익이 아니라, 중소형 교회 미디어 봉사자가 적은 시간으로 예배 화면을 안정적으로 띄우게 돕는 것이다.

**목표**

1. 준비 시간 단축: 5곡 세트 기준, 가사 입력부터 송출 준비 완료까지 15분 이내
2. 송출 안정성: 예배 중 송출 끊김·검은 화면 0건
3. 가독성: 어떤 모션 배경 위에서도 가사가 읽히는 기본 프리셋 제공
4. 운영 지속성: 무료 서비스로 유지 가능한 수준의 월 운영비 (클라우드 무료 티어 범위 우선)

**성공 지표 (출시 후 3개월)**

| 지표               | 목표      | 측정 방법                                     |
| ------------------ | --------- | --------------------------------------------- |
| 주간 송출 세트 수  | 주 50세트 | 발표 모드 진입 후 5분 이상 유지된 세트        |
| 재방문 사용자 비율 | 40%       | 4주 중 2주 이상 송출한 사용자 비율            |
| 라이브러리 활용률  | 50%       | 새로 추가된 곡 중 공유 덱에서 가져온 비율     |
| 송출 중 치명 오류  | 0건       | 송출 화면 멈춤·검은 화면 클라이언트 오류 로그 |

**비목표 (MVP에서 하지 않음)**

- 자유 배치형 디자인 편집 (캔바식 요소 드래그)
- 영상·PPT 파일 내보내기
- 코드 생성 애니메이션 배경
- 사용자 배경 업로드 (한때 4.3으로 편입했다가 2026-09-24에 없앴다. 배경은 관리자만 올린다)
- 교회·팀 워크스페이스, 공동 편집
- 성경 구절·광고 슬라이드 등 찬양 외 콘텐츠
- 유료 요금제
- Chrome 외 브라우저와 모바일 지원 (경고 배너만 표시)
- 절·후렴 태그, 반복 순서 지정, 제목 슬라이드
- 데스크톱 설치형 앱(Tauri 등). 웹(Chrome) 단일 플랫폼으로 간다
- 가사 자동 검색·수집 (CCM 크롤링, 멜론·벅스 조회). 법률 승인은 받아두었고 MVP 이후 진행

## 3. 타깃 사용자와 사용 시나리오

주 타깃은 중소형 교회의 찬양팀·미디어 봉사자다. 디자인·영상 전문성이 낮고, 주중 짧은 시간에 주일 예배 자료를 준비하며, 예배 중에는 혼자 송출을 맡는 경우가 많다.

**페르소나: 미디어 봉사자 '지훈' (20\~30대)**

- 본업이 따로 있고, 토요일 밤이나 주일 아침에 그 주 찬양 프레젠테이션을 받아 슬라이드를 만든다
- 지금은 PPT에 가사를 복붙하고 배경 이미지를 한 장씩 넣는다. 움직이는 배경은 쓰고 싶지만 영상 편집이 번거롭다
- 예배 중에는 찬양 인도자의 흐름에 맞춰 슬라이드를 넘긴다

**주요 시나리오**

1. 준비: 프레젠테이션(곡 목록)를 받아 곡별 가사를 입력하고, 곡마다 제공 라이브러리에서 움직이는 배경을 고른다
2. 다듬기: 오버레이 불투명도, 폰트, 글자 크기, 그림자를 조정해 가독성을 확보한다
3. 송출: 예배 시간에 웹 브라우저에서 바로 전체화면으로 띄우고 키보드로 넘긴다

**확정된 전제**

- 출력 방식은 웹 전체화면 송출 하나다. 영상·PPT 파일 내보내기는 MVP 범위 밖이다
- 움직이는 배경은 관리자가 올린 기본 제공 배경 갤러리 한 곳에서 고른다. 코드 생성 애니메이션 배경은 MVP 범위 밖이다

## 4. 핵심 기능 요구사항

MVP는 가사 입력, 곡 단위 모션 배경, 가독성 설정, 전체화면 송출로 구성한다.

### 4.1 가사 입력

- MVP에서는 사용자가 멜론·벅스 등에서 가사를 복사해 붙여넣는다. 서비스는 가사를 자동으로 검색·수집하지 않는다 (자동 검색은 MVP 이후, 8장)
- 곡 제목을 입력하면 '멜론에서 찾기' '벅스에서 찾기' 버튼이 나온다. 제목을 넣은 각 사이트 검색 페이지를 새 탭으로 여는 링크일 뿐, 서비스가 조회하지 않는다
- 붙여넣기 자동 정리
  - 각 줄 앞뒤 공백과 특수 공백 제거
  - 연속된 빈 줄은 하나로 합침
  - 빈 줄이 전혀 없으면 4.2 규칙대로 2줄씩 자동 분할
- 곡을 추가할 때 공유 라이브러리(4.7)에서 누군가 이미 만든 덱을 먼저 찾을 수 있다
- 입력·수정한 곡은 개인 라이브러리에 저장해 재사용한다

### 4.2 슬라이드 분할

- 가사를 빈 줄 기준으로 블록으로 나누고, 블록 하나를 슬라이드 한 장으로 만든다
- 한 슬라이드는 최대 4줄이다. 빈 줄 없이 4줄을 넘는 블록은 2줄 단위로 자동 분할한다
- 한 줄이 텍스트 박스 폭을 넘으면 자동 줄바꿈하고, 편집기에서 해당 슬라이드에 경고 아이콘을 띄워 글자 크기 조정을 유도한다
- 수동 편집: 커서 위치에서 슬라이드 나누기, 다음 슬라이드와 합치기
- 후렴 반복은 가사 텍스트에 반복 구간을 그대로 적는 방식으로 처리한다. 절·후렴 태그와 반복 순서 지정은 MVP에서 제외한다
- 제목 슬라이드는 만들지 않는다. 곡 전환은 배경 교체로 구분한다

### 4.3 곡 단위 배경

- 배경은 곡 단위로 지정한다. 한 곡의 모든 슬라이드가 같은 배경을 공유한다
- 슬라이드가 넘어가도 배경 영상은 끊기지 않고 계속 재생되어야 한다 (텍스트만 교체)

**배경은 하나의 갤러리다 (2026-09-24).**

- 모든 배경은 서비스가 라이선스를 확인해 올린 기본 제공 배경(루프 영상·정지 이미지)이다. 누구에게나 같은 갤러리로 보이고, 공개 덱과 포크에도 따라간다
- 올리기·지우기는 관리자(`ADMIN_USER_IDS`)만 앱의 배경 화면에서 한다. 올릴 때 출처·라이선스를 적고 재배포 가능 여부를 확인한다. 운영 런북으로도 등록할 수 있다
- 사용자 업로드와 계정별 용량 한도는 없앴다. 예전 사용자 업로드 행은 마이그레이션 `0002`로 지웠다
- 갤러리와 편집기 배경 선택 창은 탭 없이 한 격자에 보여 주고, 분위기·색 태그와 검색으로 거른다
- 관리자가 배경을 지우면 그 배경을 쓰던 모든 곡은 '배경 없음'이 된다
- 배경은 곡에 지정된 순간 백그라운드 캐시(6.1) 대상에 포함된다

### 4.4 오버레이, 타이포그래피, 텍스트 위치

- 배경 위 검정 오버레이, 불투명도 0\~100% 조절
- 웹폰트 기반 폰트 선택, 글자 크기, 텍스트 그림자
- 설정은 곡별로 각자 지정한다. 새 곡을 추가하면 서비스 기본 프리셋이 적용되고, 사용자가 곡마다 조정한다 (세트 일괄 적용은 MVP 이후)

**텍스트 박스 위치**는 곡 단위로 지정하고, 한 곡의 모든 슬라이드에 똑같이 적용한다. 슬라이드마다 다르게 둘 수 없다.

- 위치: 편집 캔버스에서 텍스트 박스를 드래그해 옮기고, 좌우 핸들로 폭을 조절한다. 기본값은 화면 가운데다. 3×3 위치 프리셋 격자는 드래그와 겹쳐 2026-09-25에 편집기에서 뺐다 (예전 곡에 저장된 기준점은 그대로 렌더한다)
- 높이는 가사 줄 수에 맞춰 자동으로 정해진다. 박스는 기준점에서 자라므로, 하단 기준점에 둔 박스는 줄이 늘면 위로 커진다
- 안전 여백: 박스는 화면 가장자리 5% 안쪽으로만 움직일 수 있다
- 드래그 중에는 화면 가로·세로 중앙선에 자석처럼 붙는다
- 슬라이드 중 줄 수가 가장 많은 슬라이드가 화면 밖으로 넘치면, 해당 곡에 경고 아이콘을 띄운다

### 4.5 송출 모드

- **전체화면 슬라이드쇼:** 한 화면에서 키보드(←/→, Space, PageUp/Down), 프레젠터 리모컨, 번호 입력 이동(5장 송출 단축키)으로 진행
- 송출 중 긴급 동작: 화면 검게 하기(블랙아웃), 가사만 숨기고 배경 유지
- 발표자 보기(조작 창·송출 창 분리)는 2026-09-24에 MVP에서 제거했다. 송출은 전체화면 한 가지다

### 4.6 계정

- 개인 계정만 제공한다. 교회·팀 워크스페이스와 멤버 초대는 MVP 범위 밖이다
- 계정 단위로 덱(찬양 슬라이드)과 예배 세트(프레젠테이션)를 저장한다
- **로그인은 편집의 전제 조건이다(2026-09-22 결정).** 미로그인 상태에서는 편집·대시보드·송출 어디에도 들어갈 수 없다. 초기 설계는 게스트 편집을 허용했으나, 모든 데이터가 계정에 묶이는 편이 '다른 PC에서 같은 세트를 연다'를 단순하게 만든다고 판단해 바꿨다
- **단, 로그인 확인이 예배를 막지 않는다.** 마지막으로 확인된 세션을 IndexedDB에 캐시해 두고 부팅 시 그것으로 게이트를 통과시킨다. 서버 재검증은 백그라운드로 돌린다. 예배 당일 네트워크가 끊겨도 캐시된 세션이 살아 있으면 송출은 그대로 된다
- 로컬 저장본은 세션 사용자로 걸러 싣는다. 한 브라우저를 여러 사람이 써도 남의 세트가 보이지 않고, 로그아웃해도 로컬 저장본 자체는 남는다

### 4.7 공유 라이브러리

사용자가 만든 찬양 슬라이드(가사 분할 + 배경 + 스타일)를 다른 사용자가 검색해 바로 가져다 쓸 수 있다. 새 사용자가 빈 화면이 아니라 완성된 슬라이드에서 시작하게 하는 것이 목적이다.

- **공유 단위:** 곡 1개의 찬양 슬라이드(덱). 세트(프레젠테이션) 전체 공유는 MVP 이후
- **공유 선택:** 덱마다 공개/비공개를 사용자가 선택한다. 기본값은 비공개. 공개·비공개 전환은 곡 추가 창의 내 보관함 미리보기에서 한다. 공개되는 것은 보관함 원본 그대로이며, 세트에서 고친 가사·서식은 들어가지 않는다 (2026-09-25 편집기에서 공유를 뺐다)
- **게시판 모델:** 같은 곡을 여러 사람이 공개하면 합치지 않고 각각 보여 준다 (4.8)
- **검색 및 노출 범위:** 곡 제목·아티스트·가사로 검색하고, 결과를 가져간 횟수순(같으면 최근 수정순)으로 정렬한다. 카드에 배경 썸네일과 첫 슬라이드 미리보기를 보여준다. (비로그인 공개 웹 카탈로그/랜딩 페이지에서는 저작권 보호를 위해 첫 슬라이드만 노출하며, 편집기 내부 곡 추가 모달에서는 예배 준비자가 찬양 버전과 구성을 확인할 수 있도록 가사 전문 미리보기와 가사 본문 검색, 텍스트 복사를 지원한다)
- **가져오기:** 라이브러리에서 가져오기는 기본적으로 fork다. 공유 덱을 내 라이브러리로 복제해 자유롭게 수정하고, 원본은 바뀌지 않는다. 복제본에는 `forked_from`으로 원본을 기록하고 원작자 표시와 원본 링크를 남긴다. 원본을 직접 편집하는 방식은 제공하지 않는다
- **비공개 전환·삭제:** 원작자가 비공개로 돌리거나 지워도 이미 가져간 복제본은 유지된다
- **신고:** 가사 오류·부적절한 콘텐츠 신고 기능. 저작권자 요청 시 공개를 내리는 절차를 둔다

### 4.8 가사 라이브러리와 LLM 정규화 — MVP 제외 (2026-09-23)

초기 설계는 사용자가 등록한 가사를 곡 단위로 모아, 같은 곡을 여러 사람이 올리면 LLM(Qwen3.8 27B)으로 대표 가사 하나를 만드는 것이었다. **MVP에서는 이 기능을 뺐다.** 공유는 4.7의 공유 라이브러리 하나로 운영한다.

- **게시판 모델:** 같은 곡을 여러 사람이 공개해도 합치지 않고 각각 따로 보인다. 목록은 가져간 횟수(사용수)순, 같으면 최근 수정순이다
- **가사 오류:** 대표 가사를 운영자가 고쳐 잠그는 절차 대신, 해당 공개 덱에 대한 신고·교정 제안과 게시 중단(4.7 신고)으로 처리한다
- **되살릴 때:** 곡 식별, 루트 버전 1인 1표, 입력에 없는 줄을 거부하는 검증, 최다 등록 버전 폴백 설계는 `docs/tasks/m5/tasks_4.md`에 이력으로 남아 있다

### 세트 편집기 리본 (곡 단위, 2026-09-25)

오른쪽 속성 패널을 없애고 PowerPoint '홈' 탭처럼 서식 도구를 상단 리본에 모았다. 서식은 곡 단위라 현재 곡의 모든 슬라이드에 적용된다 (4.4). 세트 일괄 적용은 하지 않는다.

- 슬라이드: 새 슬라이드(빈 슬라이드를 만들고 바로 편집), 복제, 삭제, 나누기, 합치기
- 글꼴: 폰트(번들 웹폰트 목록), 크기(pt. PowerPoint 16:9 슬라이드 기준으로 1pt = 스테이지 2px, 목록 20\~96과 직접 입력, 한 칸 키우기·줄이기), 색(팔레트 + 컬러피커), 그림자 4단계
- 단락: 왼쪽·가운데·오른쪽 정렬, 줄 간격(1.0\~2.5)
- 배경: 곡 배경 선택, '어둡게'(검정 오버레이 불투명도 0\~100%)
- 위치·폭: 캔버스에서 드래그·폭 핸들·중앙선 스냅으로만 조절한다
- 넘침 경고: 한 줄이 박스 폭을 넘으면 슬라이드 썸네일에, 줄 수가 가장 많은 슬라이드가 화면 가장자리 여백을 넘치면 곡 헤더에 경고 아이콘. 선택한 곡·슬라이드의 경고는 하단 상태 표시줄에 안내 (4.2·4.4)
- 뺀 것 (2026-09-25): 테마 프리셋, 3×3 위치 격자, 서식 초기화, 속성 패널의 공유(곡 추가 창 내 보관함으로 이동, 4.7), 캔버스의 암전·가사 숨김 미리보기
- 실행 취소: 슬라이더를 끌거나 가사를 입력하는 동안의 연속 변경은 한 단계로 묶는다(같은 항목, 1초 이내). 기록은 문서마다 100단계까지

| 키                   | 동작                               |
| -------------------- | ---------------------------------- |
| → / Space / PageDown | 다음 슬라이드                      |
| ← / PageUp           | 이전 슬라이드                      |
| `N` Enter            | 세트 전체 N번째 슬라이드로 이동    |

번호 이동 규칙:

- 번호는 PPT처럼 세트 전체에서 1부터 끝까지 이어진다. 곡이 바뀌어도 1로 돌아가지 않는다 (예: 1곡이 5장이면 2곡 첫 장은 6). 곡 단위로 건너뛰는 별도 입력은 없고, 그 곡 첫 장의 번호를 입력한다
- 숫자는 입력 버퍼에 쌓이고, Enter를 눌러야 이동한다. 숫자 키만으로 즉시 이동하는 동작은 없다
- 3초간 입력이 없으면 버퍼를 비운다
- 숫자·Enter만으로 모든 이동이 되므로 USB 숫자 키패드 하나로 조작할 수 있다
- 편집기의 슬라이드 썸네일에도 같은 세트 전체 번호를 표시한다
- 입력 중인 번호(예: `12_`)는 청중 화면에 아무것도 띄우지 않는다
- 없는 번호는 무시하고 버퍼를 비운다. 청중 화면에는 알림을 띄우지 않는다
- 송출 종료는 전체화면 해제(Esc) 또는 마우스를 올리면 나타나는 종료 버튼으로 한다

## 6. 비기능 요구사항

예배 중 송출은 절대 끊기면 안 된다. 그래서 편집과 송출 모두 로컬 저장소를 1차 원천으로 쓰고, 서버는 계정 간 동기화와 공유에만 쓴다.

### 6.1 네트워크: '온라인 편집 + 끊겨도 버티는 송출'

중소형 교회 예배당은 와이파이가 약하거나 송출 PC가 인터넷에 연결되지 않은 경우가 흔하다고 가정한다.

- 앱을 PWA로 만들고, Service Worker로 앱 셸과 웹폰트를 캐시한다
- 가사·설정은 편집할 때마다 IndexedDB에 저장되므로 송출에 네트워크가 필요 없다
- 편집기나 송출 화면에 세트가 열려 있고 온라인이면, 그 세트의 배경 영상·포스터를 뒤에서 하나씩 Cache Storage에 받아 둔다. 진행률·배지·경고 같은 UI는 없다. 받지 못한 것은 다음 기회(네트워크 복구, 다시 열기)에 다시 받는다
- 캐시된 배경은 네트워크 없이 재생된다. 캐시되지 않은 배경은 네트워크에서 스트리밍한다
- 송출 중에는 API·데이터 요청을 하지 않는다. 네트워크를 쓰는 것은 영상 재생과 배경 백그라운드 캐시뿐이다
- 백그라운드 캐시를 처음 시작할 때 `navigator.storage.persist()`로 영구 저장소를 조용히 요청한다. 거부돼도 알리지 않는다
- 송출 전에 배경을 미리 받는 '예배 준비' 화면(곡별 다운로드 상태, '오프라인 송출 가능' 배지)은 M4에서 구현했으나 2026-09-24에 제거했다. 송출 버튼은 곧바로 전체화면으로 들어간다. 제품 결정 없이 다시 넣지 않는다

### 6.2 송출 성능

- 슬라이드 전환 입력 후 화면 반영 100ms 이내
- 1080p 루프 영상 재생 중 프레임 드랍 없이 텍스트 전환 (배경 레이어와 텍스트 레이어 분리)
- 곡이 바뀔 때 다음 곡 배경을 미리 로드해 검은 화면 없이 교차 전환

### 6.3 배경 영상 규격

**사전 주입 배경**

- 1920×1080, 10\~30초 무음 루프, H.264 MP4 단일 포맷 (Chrome 전용이므로 WebM 불필요)
- 파일 크기 목표 곡당 20MB 이하 (오프라인 캐시 용량 고려)

**관리자 앱 업로드 (4.3)**

- 허용 포맷: H.264 MP4, 그리고 정지 이미지 JPEG·PNG·WebP
- 파일 1개당 30MB 이하 (Worker가 요청 본문을 한 번에 받는다). 계정별 총량 한도는 없다
- 권장 해상도는 1920×1080이다. 그보다 작은 영상은 업로드는 되지만 송출 시 확대되어 흐려질 수 있다고 경고한다
- 업로드된 영상의 소리는 송출에서 항상 음소거한다

### 6.4 지원 환경

MVP는 데스크톱 Chrome 최신 버전 하나만 공식 지원한다. 개발·QA·성능 목표(6.2)는 모두 Chrome 기준이다.

- 지원 대상: Windows·macOS의 데스크톱 Chrome 최신 안정 버전
- Chrome이 아닌 브라우저(Edge, Safari, Firefox, Whale 등)와 모바일은 접속을 막지 않고, 상단에 경고 배너만 띄운다
  - 문구 예: "이 서비스는 Chrome에 최적화되어 있습니다. 예배 송출은 Chrome에서 진행해 주세요."
  - 배너는 닫을 수 있고, 닫은 상태는 브라우저에 기억한다
  - 송출(전체화면) 진입 시에는 한 번 더 확인 대화상자를 띄운다
- 판별은 User-Agent Client Hints의 브랜드 목록에 'Google Chrome'이 있는지로 한다. 같은 Chromium 기반인 Edge·Whale도 경고 대상이다
- 비 Chrome 브라우저의 버그는 MVP에서 수정 대상이 아니다. 사용 통계를 보고 지원 확대를 결정한다

### 6.5 편집 UI 테마

편집·관리 화면은 라이트·다크 두 테마를 제공한다. 토요일 밤 작업과 밝은 사무실 작업이 모두 흔해서다.

- 기본값은 운영체제 설정을 따르고, 사용자가 고른 값은 브라우저에 기억한다
- 테마는 편집기·대시보드·라이브러리 등 관리 화면에만 적용한다
- **송출 화면(전체화면)은 테마와 무관하게 항상 검정 배경으로 고정한다.** 예배 화면 색이 사용자 설정에 따라 달라지면 안 된다
- 16:9 스테이지 내부 렌더링(배경·오버레이·가사)은 편집 미리보기에서도 송출과 동일하게 그린다. 테마는 스테이지 바깥 UI에만 영향을 준다

### 6.6 저작권

- 가사: 서비스는 MVP에서 공유 덱을 통해 사용자가 입력한 가사를 보유·제공한다. 크롤링(CCM 한정), 멜론·벅스 보완 조회, 공개 공유 모두 비영리 조건으로 법률 검토를 통과했다 (9장). 약관에 사용자의 교회 저작권 라이선스(예: CCLI) 범위 내 사용 책임과 권리자 요청 시 게시 중단 절차를 명시
- 배경 영상: 재배포 가능한 라이선스를 확보한 영상만 주입한다

## 7. 기술 스택과 아키텍처

Vite 기반 React SPA와 Hono API를 하나의 Cloudflare Worker로 배포하고, 데이터는 D1·R2, 인증은 Better Auth로 구성한다.

이 스택을 택한 이유는 세 가지다.

- **영상 전송비:** R2는 송신(egress) 요금이 없어, 무료 사역 서비스의 최대 운영비인 배경 영상 전송비가 사라진다
- **한국 소셜 로그인:** [Better Auth](https://better-auth.com/docs/authentication/naver)가 카카오·네이버 제공자를 기본 제공한다
- **개발 경험:** [Cloudflare Vite 플러그인](https://developers.cloudflare.com/workers/vite-plugin/)으로 Vite HMR을 쓰면서 로컬에서도 실제 Workers 런타임(workerd)과 D1·R2 바인딩으로 개발한다

### 7.1 스택 구성

| ------------- | ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 7.2 렌더링 구조

슬라이드는 캔버스 이미지가 아니라 DOM 레이어로 그린다. 편집 미리보기와 송출 화면이 같은 컴포넌트를 쓴다.

1. 배경 레이어: `<video autoplay muted loop playsinline>`, 곡이 바뀔 때만 교체
2. 오버레이 레이어: 검정 배경 + opacity
3. 텍스트 레이어: 웹폰트, 크기, 그림자(text-shadow). 박스 위치·폭은 스테이지 대비 %로 저장해 모든 창에서 같은 자리에 그린다. 슬라이드 전환 시 이 레이어의 글자만 바뀜

16:9 고정 비율 스테이지를 만들고 CSS transform scale로 화면에 맞춘다. 편집기 미리보기와 전체화면 송출에서 동일한 레이아웃이 나온다.

### 7.3 송출 구조

송출은 한 창에서 한다. 드라이브 목록이나 편집기의 송출 버튼을 누르면 같은 창이 곧바로 전체화면으로 바뀌고, 조작자는 키보드·프레젠터 리모컨·숫자 키패드로 진행한다. 프로젝터로 내보낼 때는 이 창을 보조 모니터로 옮기거나 화면 복제를 쓴다.

발표자 보기(조작 창 + `window.open` 송출 창, BroadcastChannel 동기화, Window Management API 배치)는 M4에서 구현했으나 2026-09-24에 제거했다. 제품 결정 없이 다시 넣지 않는다.

### 7.5 구현 시 주의점

- RLS가 없으므로 모든 쿼리는 Hono 미들웨어에서 세션의 user\_id로 범위를 제한한다. 쿼리 헬퍼를 한 곳에 모아 누락을 막는다
- D1은 SQLite 기반이라 JSON 기능이 Postgres보다 제한적이다. 검색은 FTS5 trigram과 LIKE를 병행한다 (7.6)
- Better Auth는 D1에 직접 어댑터가 없어 Drizzle(또는 Kysely)을 통해 연결하고, 요청 핸들러 안에서 인스턴스를 만든다
- 착수 첫 1\~2일에 'Vite + Hono + D1 + Better Auth(카카오·네이버) + R2 영상 재생' 최소 구성을 먼저 올려 배포 파이프라인까지 확인한다
- 공개 덱 조회 API는 로그인 없이도 열 수 있으므로, 비공개 덱이 섞여 나오지 않도록 `visibility` 조건을 쿼리 헬퍼에 강제한다

**직접 구현하는 것:** 슬라이드 스테이지(3레이어 렌더링), 번호 입력 버퍼. 브라우저 기본 API로 충분하고 서비스의 핵심이라 직접 통제한다. Reveal.js 같은 발표 프레임워크는 곡 단위 배경 유지·레이어 분리 구조와 맞지 않아 쓰지 않는다.

**참고용:** [FreeShow](https://github.com/ChurchApps/FreeShow)는 단축키 UX 레퍼런스로만 본다. 카피레프트 라이선스일 수 있어 코드는 가져오지 않는다.

모든 라이브러리는 MIT 등 허용형 라이선스만 쓴다.

### 7.8 저장소 구조와 공유 타입 시스템

프론트엔드와 API를 한 저장소의 한 패키지에서 관리하고, 도메인 스키마를 공유 레이어 한 곳에서 정의해 양쪽이 같은 타입을 쓴다. 구체적인 타입 정의는 이 문서의 범위가 아니다.

**도구:** pnpm 단일 패키지(워크스페이스 없음). 배포 단위가 Worker 하나로 고정되어 있어 패키지를 나누지 않는다(2026-09-24에 워크스페이스 6개를 하나로 합쳤다). 레이어 경계는 패키지 대신 ESLint import 규칙으로 강제한다.

| 경로       | 역할                                                                             | 비고                                                                      |
| ---------- | -------------------------------------------------------------------------------- | ------------------------------------------------------------------------- |
| src/client | Vite SPA                                                                         | Worker와 함께 Cloudflare Vite 플러그인으로 빌드·배포하는 하나의 배포 단위 |
| src/worker | Worker(Hono API)                                                                 |                                                                           |
| src/shared | 도메인 스키마, API 요청·응답 계약, 공통 상수(스타일 기본값·허용 범위, 단축키 등) | `#shared`로 import. 브라우저와 Workers 양쪽에서 도는 순수 TypeScript      |
| src/db     | Drizzle 스키마, 쿼리 헬퍼(7.5의 user\_id·visibility 강제 포함)                   | `#db`로 import. Worker에서만 import                                       |
| migrations | D1 마이그레이션                                                                  | drizzle-kit이 생성하고 FTS5 SQL은 손으로 덧붙인다                         |

**공유 타입 원칙**

- 단일 원천: 도메인 스키마는 src/shared의 Zod 스키마로 한 번만 정의하고, TypeScript 타입은 그 스키마에서 추론한다. 같은 구조를 손으로 다시 쓰는 중복 타입은 만들지 않는다
- API 계약: 서버는 공유 스키마로 요청을 검증하고(@hono/zod-validator), 프론트엔드는 Hono RPC 클라이언트(hc)로 API를 호출해 경로·요청·응답 타입을 컴파일 시점에 맞춘다
- DB와 API 분리: DB 행 타입은 Drizzle에서 추론하고, API로 내보내는 구조는 공유 스키마로 따로 정의한다. DB 구조를 API에 그대로 노출하지 않는다
- JSON 컬럼: `decks.style`·`decks.slides`처럼 D1에 JSON TEXT로 저장하는 값은 공유 스키마로 구조를 정하고, 저장·조회 시 스키마로 검증한다
- 의존 방향: shared ← db ← worker, shared ← client 한 방향만 허용한다. 프론트엔드 코드가 src/db를 import하면 ESLint 규칙으로 막는다
- CI는 저장소 전체 타입 검사를 한 번에 돌려, 스키마 변경이 양쪽 모두에 즉시 반영되게 한다

## 8. MVP 범위와 로드맵

출시 일정은 미정이므로 기간 대신 마일스톤으로 진행한다. 마일스톤 규칙은 세 가지다.

1. 각 마일스톤은 앞 마일스톤의 완료 기준을 충족한 뒤 '완료'로 선언한다. 화면을 먼저 만들어 보는 선행 구현은 막지 않되, 완료 기준을 충족하기 전까지 그 마일스톤을 완료로 세지 않는다
2. 완료 기준은 '실제 예배에서 송출했다', '다른 계정에서 가져와 띄웠다'처럼 관찰 가능한 사실로만 쓴다. 진행률이나 '대부분 구현'은 완료가 아니다
3. M1부터는 매주 주일 예배 실사용으로 검증하고, 거기서 나온 문제를 다음 주 작업의 맨 앞에 둔다

### 현재 구현 현황 (2026-09-23 기준, 3차 갱신)

로드맵은 실제 코드 상태를 반영해 한 번 조정했다. 그간 UI를 먼저 만들고 데이터 계층을 뒤로 미루는 방식으로 진행해, 편집기 완성도는 M2 수준이지만 저장은 전혀 없는 상태다.

- **된 것:** 모노레포·Worker 배포 파이프라인, D1·R2 바인딩, 3레이어 스테이지, 전체화면 송출과 키보드·번호 이동, 붙여넣기 자동 정리와 자동 분할, 세트 편집기(PPT식 슬라이드 썸네일 창, 텍스트 박스 드래그·리사이즈, 상단 리본 도구 모음, 캔버스 직접 가사 편집), 2-Pane 곡 추가 모달, 대시보드·배경 라이브러리 화면, 라이트·다크 테마
- **저장(M3-A) 완료:** 프레젠테이션과 곡 보관함을 IndexedDB(`worship-offline-db`)에 저장한다. 브라우저를 껐다 켜도 세트가 그대로 남고, 저장에 실패하는 환경에서는 닫을 수 없는 경고 배너를 띄운다. 실사용 검증에서 데이터 손실 결함 1건(곡 복제 시 세트 전체 소실)과 송출 결함 1건(블랙아웃이 가사를 못 가림)을 찾아 고쳤다
- **계정·서버 저장(M3-B) 코드 완료:** 카카오·네이버 로그인(Better Auth), 덱·프레젠테이션 문서 단위 CRUD API, Hono RPC 클라이언트, 문서 단위 LWW 동기화. **남은 것은 실제 OAuth 자격증명으로 2대 PC에서 확인하는 것이다**
- **오프라인·예배 준비(M4) 코드 완료:** PWA Service Worker가 앱 셸을 프리캐시하고 배경 영상을 `worship-videos-cache`에 담는다. 함께 만든 발표자 보기(7.3)와 예배 준비 화면은 2026-09-24에 제거했고, 이제 편집·송출 중에 세트의 배경을 조용히 받아 둔다(6.1). **헤드리스 Chrome에서 네트워크를 끊은 채 5곡 세트를 완주하는 것까지 확인했다. 남은 것은 실제 보조 모니터(프로젝터) 확인과 주일 예배 송출이다**
- **공유 라이브러리(M5) 코드 완료:** 덱 공개 설정(저작권 안내 동의), 공개 덱 검색(가져간 횟수순 게시판)과 가져오기, 신고와 운영자 게시 중단(SQL 런북). 샘플 공유 곡은 지웠다. **두 계정으로 공개 → 검색 → 가져오기 → 무수정 송출을 브라우저와 테스트로 확인했다.** 가사 라이브러리와 LLM 정규화는 MVP에서 제거했다(2026-09-23, 4.8). **운영 D1 마이그레이션이 남았다**
- **로드맵 조정 배경:** M1·M2의 완료 기준인 '실제 예배 송출'은 저장 없이 검증할 수 없었다. 그래서 M3을 '저장'으로 재정의하고 **로컬 영속성(M3-A)을 계정 로그인(M3-B)보다 앞에 뒀다.** 이 코드가 M4 오프라인 캐시의 토대가 된다

M6 가사 시드는 별도 개발 없이 운영자가 직접 콘텐츠를 채우는 단계다. 가사 입력 자체는 M3-B부터 개인 계정으로 틈틈이 시작하고, 공유 기능이 열리는 M5 이후 공개로 전환한다. 시드 가사는 운영자 계정의 공개 덱으로 올린다.

가사는 MVP 내내 붙여넣기로 입력한다. 자동 검색·수집은 MVP 이후다.

### 배경 영상 확보

MVP 배경 영상은 20개로 시작하고, 직접 제작을 기본으로 한다. M0에 10개, M6까지 20개를 확보한다.

- 직접 제작: 그라데이션·빛·입자 계열 추상 루프 영상을 모션 툴로 만든다. 라이선스 문제가 없다
- 무료 스톡(Pexels, Pixabay 등): 라이선스 문서에서 서비스 내 재배포가 허용되는 것이 확인된 영상만 쓴다. 확인되지 않으면 쓰지 않는다
- 분류 태그: 분위기(잔잔한 / 밝은 / 웅장한)와 주조색(따뜻한 / 차가운 / 어두운) 두 축

- 가사 라이브러리(4.8) 재도입 검토: 곡 단위 대표 가사와 LLM 정규화, CCM 크롤링 + 멜론·벅스 보완 조회를 소스로 추가 (비영리 조건 법률 승인 완료, 9장 원칙 적용)
- 세트 전체 스타일 일괄 적용, 스타일 프리셋 저장
- 교회·팀 워크스페이스와 공동 편집
- 태블릿·폰 원격 조작
- 성경 구절·광고 슬라이드
- 사용자 영상 업로드, 코드 생성 애니메이션 배경

## 9. 리스크와 운영 원칙

MVP에서 가사는 사용자가 붙여넣고, 서비스는 공유 덱으로 가사를 제공한다. 공개 공유는 비영리 조건으로 법률 검토를 통과했다. 가사 크롤링(CCM 한정)과 멜론·벅스 조회도 승인받았지만 MVP 이후에 도입하며, 도입 시 아래 원칙을 따른다.

| 리스크                       | 영향                                                    | 대응                                                                                   |
| ---------------------------- | ------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| 가사 공개 공유               | 비영리 승인 범위를 벗어나면 공중송신권 문제가 다시 생김 | 비영리 조건으로 승인. 기본 비공개, 공개 시 안내 동의, 권리자 요청 시 게시 중단 절차    |
| 붙여넣은 가사 오류           | 잘못된 가사로 예배 중 혼선, 공유 시 확산                | 붙여넣기 자동 정리, 공유 덱 교정 신고, 가져오기 수 기반 정렬                           |
| 공유 덱 품질·부적절 콘텐츠   | 검색 결과 신뢰 하락                                     | 신고 기능, 운영자 숨김 처리                                                            |
| 배경 영상 라이선스           | 재배포 불가 영상 사용 시 분쟁                           | 재배포 허용 라이선스 영상만 주입, 출처 기록                                            |
| 관리자 계정 탈취             | 부적절한 배경이 모든 사용자에게 노출                    | 관리자를 이메일이 아닌 user id(`ADMIN_USER_IDS`)로 지정, 필요할 때만 목록에 넣기 (4.3) |
| 예배당 네트워크 불안정       | 송출 중단                                               | 오프라인 송출 구조 (6.1)                                                               |
| 무료 서비스의 영상 전송 비용 | 사용자 증가 시 운영비 증가                              | R2 무료 송신으로 전송 요금 해소. 영상 용량 제한(6.3)과 브라우저 캐시로 로딩 부담 관리  |

**가사 수집 운영 원칙 (MVP 이후 도입 시)**

- 수집 대상은 법률 검토를 통과한 CCM 소스 목록으로 한정한다. 새 소스는 재검토 후 추가한다
- robots.txt나 이용약관이 수집을 금지하는 사이트는 대상에서 뺀다
- 요청 간격을 제한하고, 서비스를 식별할 수 있는 User-Agent를 쓴다
- 수집한 가사마다 출처 URL과 수집 시각을 기록하고, 권리자 요청 시 곡 단위로 즉시 삭제한다
- 멜론·벅스 조회는 도입 전 기술 검증을 거친다. 기준: 소스별 CCM 20곡 중 18곡 이상 정확, 곡당 10초 이내, 3일 연속 동일 결과. 통과한 소스만 연동하고, 운영 중에는 요청 시 1곡씩만 조회한다
- 유료화·광고 도입 등으로 비영리 조건이 바뀌면 크롤링·보완 조회·공개 공유 전체를 다시 법률 검토한다
